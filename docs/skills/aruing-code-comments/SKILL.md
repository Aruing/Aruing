# Code Comments

## 作用范围

只处理当前任务明确涉及的文件、符号和注释。不要为了满足注释规范扩大修改范围

普通代码修改时，只有当已有注释会过期、错误，或用户明确要求补充、修改、审查注释时，才应用本 skill

如果发现任务范围外存在大量缺失、过期或不一致的注释，只说明具体问题和建议，不要直接补齐

## 核心原则

生成、修改或补充代码注释时，注释要帮助后来的人快速理解边界、意图和关键选择。注释必须使用中文，保持简洁、有逻辑，不要堆砌解释，也不要只是把代码表面含义翻译一遍

修改已有代码时，只检查当前任务涉及范围内的注释是否缺失、过期、错误或不够完整。即使用户只要求补充某一部分注释，也只在该任务范围内判断模块、结构体、字段、函数和关键步骤是否需要同步调整

用户已经写过的注释默认属于用户已有表达，不要为了统一风格、补充细节或个人判断擅自改写、移动或删除。只有当前任务明确要求修改该注释、重写该范围注释、删除该注释，或用户已经确认修改方案时，才可以直接改动已有注释

如果发现已有注释确实存在问题，但问题没有被当前任务明确覆盖，先说明具体问题和建议改法，等待用户确认后再修改。即使任务范围覆盖了相关代码，只要涉及改写或删除用户已经写过的注释，也优先询问确认；可以新增缺失注释，但不要顺手重写已有注释

## 必须覆盖

| 位置 | 要写什么 |
| --- | --- |
| 模块顶部 | 当前模块的边界、主要功能、依赖关系、调用约定、需要注意的问题 |
| 结构体或类型定义前 | 该结构承载的领域含义、主要功能、使用位置、生命周期、调用方需要理解的边界 |
| 结构体字段前 | 字段含义、取值来源、单位或格式、默认值语义、特殊用法、设置或读取时的注意事项 |
| 每个函数或方法前 | 函数负责什么、输入输出语义、错误或副作用、调用方需要注意的约束 |
| 关键实现步骤 | 为什么这样做、这个步骤承担的目标、顺序或条件背后的原因 |

模块注释写在文件或模块的顶部。结构体注释写在类型定义前，字段注释写在字段定义前。函数注释写在函数或方法定义前。关键步骤注释写在最靠近对应逻辑的位置

## 写法要求

- 全部注释使用中文，不要中英混写
- 不要用模块名、结构体名、字段名、函数名、方法名作为注释开头，除非目标语言或项目检查强制要求
- 句末不需要使用句号或英文句点
- 优先说明意图、边界、约束、原因和注意事项
- 简单字段也必须说明含义，不要因为字段名看起来直观就省略注释
- 结构体字段注释不要在每个字段之间机械空行，原则上连续书写；只有字段可以分为几个具有内在关联的逻辑部分时，才在各部分之间空一行
- 有特殊用法、默认行为、单位、格式、并发约束、持久化语义或兼容性要求时，必须写清楚
- 关键步骤注释要解释实现选择，不要复述代码已经表达清楚的内容
- 注释要短，复杂逻辑可以拆成几条有顺序的注释
- 修改已有代码时，同步补齐或更新相关模块、结构体、字段、函数和关键步骤注释
- 对已有注释保持最小改动，发现问题但没有明确授权时先询问

## 已有注释处理边界

| 情况 | 处理方式 |
| --- | --- |
| 任务明确要求补齐缺失注释 | 可以新增缺失注释，不要顺手改写已有注释 |
| 任务明确要求重写、修正或删除某段注释 | 可以按要求修改指定注释 |
| 任务范围包含已有注释，但没有明确要求修改它 | 保留原注释；如发现问题，先询问 |
| 代码改动导致已有注释可能过期或错误 | 先指出原因和建议改法，等待确认后再改 |
| 为了风格统一、措辞更好或更完整而想改已有注释 | 不要直接改，先询问 |

询问时要具体说明：哪条注释有问题、为什么有问题、建议如何改。不要只说“这里注释需要优化”

## 好的注释

```go
// 保存一次运行所需的完整参数集合，只在初始化完成后传给执行层
// 字段值应来自统一校验后的配置，避免调用方重复处理默认值
type runtimeOptions struct {
    // 请求可等待的最长时间，零值表示使用执行层默认限制
    timeout time.Duration
    // 是否启用详细日志，仅用于排查问题，不应改变业务流程
    verbose bool
}

// 负责把运行时配置转换为后续组件可以直接消费的参数集合
// 这里不读取外部资源，避免初始化阶段产生隐藏副作用
func buildRuntimeOptions(cfg Config) runtimeOptions {
    // 先合并默认值，确保后续校验只面对完整配置
    options := mergeDefaults(cfg)

    // 用户显式传入的限制优先级最高，避免被环境变量覆盖
    applyUserLimits(&options, cfg)

    return options
}
```

```ts
// 只处理已经完成鉴权的请求，未鉴权状态应在路由守卫中提前拦截
function createSessionContext(request: Request): SessionContext {
  // 保留原始用户标识，后续审计日志需要和入口请求保持一致
  const userId = request.user.id

  return { userId }
}
```

## 避免的注释

```go
// RuntimeOptions stores runtime options.
type RuntimeOptions struct {
    Timeout time.Duration
    Verbose bool
}

// buildRuntimeOptions builds runtime options.
func buildRuntimeOptions(cfg Config) RuntimeOptions {
    // set options
    options := mergeDefaults(cfg)

    return options
}
```

问题：

- 使用英文
- 结构体和字段没有注释
- 以类型名或函数名开头
- 只是复述代码，没有说明边界、意图、约束或注意事项
- 关键步骤注释太空泛

## 自检清单

提交代码前检查：

- 新模块顶部是否有模块注释
- 新增或修改的结构体、类型定义是否有中文注释
- 结构体每个字段是否都有中文注释，包括看起来很简单的字段
- 结构体字段注释是否避免了频繁空行，只在有内在关联的字段分组之间空行
- 每个新增或修改的函数、方法是否有中文注释
- 关键步骤是否说明了目标、原因或注意事项
- 修改代码后，相关注释是否仍然准确，是否需要同步补充或删改
- 指定补充某一部分注释时，该范围内的相邻定义是否也存在明显缺口
- 是否误改、移动或删除了用户已有注释
- 对已有注释发现问题但没有明确授权时，是否先询问用户确认
- 是否存在英文注释、机械翻译、过长段落或无意义注释
- 注释是否随着实现变化同步更新
